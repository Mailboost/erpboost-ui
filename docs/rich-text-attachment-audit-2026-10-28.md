# リッチテキストと添付の境界確認（2026-10-28）

参照: https://ui.tailor.tech/  
公開先: https://mailboost.github.io/erpboost-ui/

前回の選択・検索の確認に続き、リッチテキストの書式・リンク・リスト・表のキーボード編集と、添付のファイル種別・サイズを比較した。**添付の選択候補、リンクの判定、全文選択したリストの操作に差があり、カタログのデモ内で合わせた。**

全ページの全操作・全画素が完全一致したという判定ではない。参照側にもある制約の再現と、正常な操作の成功を区別する。

## 合わせた差分

| 対象 | 修正前 | 修正後 |
| --- | --- | --- |
| 添付のファイル種別 | 選択用inputの`accept`が未設定で、画像・PDFに候補を絞らない | 参照と同じ`image/*,application/pdf`をデモで指定。汎用AttachmentやuseAttachmentの既定値は変更しない |
| リンク判定 | URL入力に`example.com/path`を指定すると、そのまま相対リンクを作る | 参照の旧Tiptapの判定に合わせ、この入力をリンクにしない。HTTPS・メール・電話・SMS・FTP・`/relative/path`、入力中の自動リンクは保持。現在のTiptapの危険なURLを拒否するチェックも併用する |
| リストの全文選択 | 文書全体が1つのリストの場合、Ctrl/Cmd+Aで選択して同じリストボタンを押すとリストを解除する | 参照と同じく解除しない。デモのツールバーだけに限定。リスト種別の切替、行単位の解除は動く。これは参照側の制約に合わせたもので、全文選択による解除の改善ではない |

リンクとリストの差は、参照サイトの実操作と配信中のTiptap実装、ローカルの依存ライブラリの実装を照合した。Tiptap全体のバージョンやDocumentページのエディタは変更していない。

反映前の公開版でも、`accept`未指定・`example.com/path`のリンク化・全文選択したリストの解除を確認した。開発環境だけに出る差ではない。

## 追加した操作確認

Playwright Chromiumで、共通7シナリオをPC 1280×900・ライト、モバイル375×812・ダークで確認した。新規14ケース／環境。

| 対象 | 操作・確認内容 |
| --- | --- |
| 見出し・書式 | 見出し1→2→3→段落、太字・斜体・下線・取り消し線の重ねがけ。選択した文字列を保持し、Undoで最後の書式だけを外し、Redoで戻す |
| リスト | 箇条書きをTabで入れ子にし、Shift+Tabで戻す。番号付きへ変換。全文選択での同種ボタンは解除せず、別種への切替はできる。各行へカーソルを置けば段落へ戻せる |
| リンク入力 | URLのpromptの文言と初期値、HTTPS・メール・電話・SMS・FTP・相対パス、`target` / `rel`、再クリックでの解除、キャンセル・空欄・`example.com/path`・javascript / dataの拒否 |
| 自動リンク | 実キー入力でHTTPS、ドメインのみ、FTPを入力し、末尾の空白でリンクを作る。表示文字列とhrefを照合 |
| 表 | 3×3表の挿入、ヘッダ入力、Tab移動、最後のセルからTabで4行目を追加、Shift+Tabで前行の末尾へ戻り、再びTabで追加行へ移動して編集 |
| ClearとSave | 全消去とplaceholder、Undoで初期文書を復元、Redoで再消去。Saveでは画面内の文字列が残るが、再読込で初期文書へ戻ることを確認 |
| 添付の境界 | `accept`と複数選択、PDFのMIME型・拡張子を指定した20,000,000バイトと20MiB+1バイトのファイル、日本語名のテキストをまとめて追加し、個別に削除。inputの値が空へ戻ることも確認 |

ツールバーの操作後はエディタへのフォーカス復帰を待って次のキーを送る。表のセルやリスト行をマウスで選んだ後は、ブラウザの`selectionchange`が処理される描画フレームを待つ。選択の反映前に次のキーを送り、別のセルやボタンへ入力した状態を正常な編集結果と取り違えない。エディタ内部のコマンドをテストから直接呼んで結果を作ってはいない。

## 参照側にもある制約

1. **リストの全文選択による解除:** 文書が1つのリストだけのとき、Ctrl/Cmd+Aで文書全体を選択して同じリストボタンを押しても解除されない。別のリスト種別への切替と、行にカーソルを置いての解除は可能。新しいTiptapで改善されている部分を、カタログの比較では参照と同じ挙動に限定した。
2. **「20MBまで」は強制されない:** PDFとして渡した20,000,000バイトと、20MiBを1バイト超えるファイルの両方を追加できた。サイズ確認用にバッファを生成し、MIME型と拡張子を指定したもので、PDF構文の妥当性は検証していない。`accept`はファイル選択の候補を絞る属性であり、サイズやファイル内容の検証ではない。Playwrightのfile chooserへファイルを指定すると、`.txt`も追加できる。OS標準のファイル選択画面で、絞り込まれたファイルを目視選択できたという証明ではない。
3. **Saveと文字数:** Saveには保存ハンドラーがなく、文字数も`— characters`のまま。画面内の編集結果が残ることと、サーバー永続化の成功を混同しない。

上記を含む3シナリオ×2画面条件の6ケース／環境には`reference-limitation`注記を付けた。テストの通過は制約を含む結果が一致したという意味で、これらの機能が正常に完成しているという判定ではない。

## 画像比較

書式を重ねた見出し、挿入直後の空の表、4行目を追加・編集した表をPC・モバイルで撮影した。フォント読み込み・フォーカス復帰・選択反映を待ち、同じコンポーネント領域を比較した。

ローカル6比較では5比較が差分0画素、PCの書式変更後の枠に9画素の差があり、RGB各チャンネルの最大差は1／255だった。表はTiptapのバージョンによってDOMのラッパー・属性が異なるが、今回撮影したPC／モバイルの空・編集済み表の4比較は差分0だった。

公開反映後の6比較も同じ結果だった。参照対ローカル・参照対公開版の計12比較中10比較が差分0画素、残る2比較はそれぞれ9画素・チャンネル最大差1／255だった。小さな差を0として扱わず、範囲と数値をJSONに保存する。

特定の状態・サイズの撮影結果であり、全入力・全アニメーションフレーム・全ブラウザの一致保証ではない。
