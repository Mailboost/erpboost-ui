前回のメール・添付に続き、通知、承認の状態遷移、承認ルート／フォームの編集を実ブラウザで追加確認した。**今回の確認範囲では新しいアプリ実装の差分は見つからず、アプリコードは変更していない。検証を追加し、全画面のエラー画面が明記されていなかった過去の記録を訂正する。**

## 追加した操作確認

PlaywrightのChromiumで、PC 1280×900・ライトと、モバイル375×812・ダークを使用した。各環境で通常操作14ケースと、既知の全画面エラーの再現1ケースを確認する。参照・ローカル・公開版で計45ケースが成功した。**エラー再現の3ケースは、プレビューの機能が使える成功ケースではない。**

| 対象 | 確認した操作・結果 |
| --- | --- |
| 承認完了 | 3段階を順番に承認。次の段階だけがPendingになり、コメントをtrimして保持、入力欄は次段階で空になる。全承認後は操作欄がなくなり、Resetで初期段階へ戻る |
| 差し戻し | 途中段階から差し戻すと、それ以前の承認済みコメントは保持。後続はWaitingのままで、承認／差し戻しの入力欄がなくなる。Resetと空白コメントも確認 |
| 承認人数 | 承認者を減らすとQuorum表示・JSONのminを人数へ制限。承認者を増やすと元の設定値へ戻る。人物／役割の種類、0人時の警告、空ルート、段階再追加のJSONも確認 |
| 承認者選択のEscape | 候補が開いているときはEscapeで閉じ、選択を保持。候補が閉じた状態で再度Escapeを押すと、その段階の承認者を全解除する。他段階の承認者は保持。参照・実装で同じ |
| フォームの既存項目 | ラベル・placeholder・help text・必須の編集、選択肢削除後の番号付け直し、選択肢0件からの再追加、選択解除、編集前後の項目ID保持をJSONで照合 |
| フォームの種類・空表示 | 全8種類を追加して13項目の型を照合。選択中の項目削除、必須件数、全項目削除後の空表示、空状態から再追加、再読込で初期5項目へ戻ることを確認 |
| 通知 | 通常カタログでTabによるフォーカス移動、矢印でタブへ移動してEnterで切替、1件既読、全件既読、Unreadの空表示、Escape／外側クリックで閉じる、再表示時の状態、サイドバーの件数を確認 |
| 全画面の既知エラー | Sidebar / User profile dialog / Notification panelの3ルートは、両サイトで同じProvider不足のエラーを表示する。機能の成功に数えず、正常表示の比較から除外する |

承認処理はサンプル内の状態遷移で、時刻は固定の`Jul 15, 2026 10:24`。実際の承認APIや通知送信の成功を確認したものではない。

## 過去の記録の訂正

全画面プレビューの`/patterns/notification-panel`でも、参照・実装の両方が`useSidebar must be used within a SidebarProvider.`を表示することを確認した。これまで本文に明記していたSidebar / User profile dialogに追加する。

以前の計測では通知パネルの参照・実装とも要素数が3で、`measurementDiffs: 0`だった。これはエラー画面の見出し・説明・再試行ボタンが一致した結果を含んでおり、通知のUIが表示された証拠ではない。元の計測値は残し、該当ルートへ`matching-reference-error`の分類を追加した。

さらに、768×1024・ダークの全画面67ルートを参照・公開版の両方で再読込した。各サイトとも67件がHTTP 200、64件はmainに本文があり、上記3件はエラーバウンダリーを表示した。未確認・空表示・追加のpageerrorは0件。これはエラーの分類確認であり、全ルートの全操作を再検証した意味ではない。

通常カタログの通知パネルは表示でき、操作確認はこの経路で行った。全画面のProvider不足を、ERPboostだけ正常表示する変更にはしていない。

## 参照にもある制約・仕様

- 通知パネルを閉じて開き直すと、既読状態は初期化される。パネルで全件既読にしても、サイドバーの件数は初期サンプルの3のまま。
- モバイルでの通知操作は、実際のTabキーによる移動でコンテナの横位置が変わる経路も確認した。初期表示でパネル全体が画面内へ収まるという意味ではない。
- 承認者の候補が閉じた状態でのEscapeは、選択の全解除になる。候補を閉じるだけの操作と区別する。
- 承認者0人の場合も、QuorumのJSONは`min: 1`となり、画面には「この段階はスキップされる」という警告が出る。実際のワークフローでスキップ処理が行われるかは未検証。
- フォーム／承認ルートのSave・Discardにはこのサンプルでは保存／破棄処理がなく、押しても編集状態が残る。JSONは現在の画面内の編集状態から生成するもので、バックエンド永続化ではない。
- フォームビルダーのNumber / Date / Checkbox等は設計中の見本としてdisabled。実際の申請フォームを送信したり、必須・メール形式を検証する画面として操作成功に数えていない。
- 候補を続けて検索する検証では、候補のDOMが閉じ切り、入力が空になったことを待ってから次の入力を行った。初回の検証で置いた「Escapeは選択を変えない」「矢印だけでタブを選択できる」という仮定は参照の実動作に合わせて訂正した。

## 画像比較

承認完了・差し戻し・メール項目を追加して必須／ヘルプ／ラベルを編集した状態を、PCとモバイルで撮影した。6状態について、参照対ローカル・参照対公開版の計12比較は、撮影画像の差分0画素だった。フォームのランダムなIDを表示するJSON欄は、この画像比較では開いていない。

通常カタログの通知プレビューも、フォント読み込み完了後に952×550の撮影領域で参照・ローカルを比較し、差分0画素を確認した。アプリ名が異なるカタログのサイドバーはこの領域に含めていない。

これは特定の撮影状態の比較であり、全ページ・全入力・全画素の完全一致とは判定していない。
